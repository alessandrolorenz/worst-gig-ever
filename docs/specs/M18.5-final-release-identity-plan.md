# M18.5 — Final Release Identity (plan)

**Status:** executed 2026-09-04. Written from the audit, alongside the work
rather than a week before it, because the migration was scoped by what the
audit found rather than by what was expected.

## Why now and not later

An Android application id is effectively permanent once an app is published,
and changing it makes Android treat the result as a **different application** —
every installed build stops upgrading.

V2 is internationalization, which is a decision to reach more people. Every one
of them would install a build that this migration would later invalidate. At
this moment the installed base is one phone belonging to the owner. That is the
entire argument for doing an unglamorous rename before a headline feature.

## The contract being established

| | Value |
|---|---|
| Product name | `Worst Gig Ever` |
| Expo slug | `worst-gig-ever` |
| Android package | `com.worstgigever.app` |
| iOS bundle identifier | `com.worstgigever.app` |

Recorded authoritatively in `docs/release/product-identity.md`, with the rule
that no future identifier may be derived from *Worst Band Ever*, and the policy
that the title is never translated.

## Scope

In: the identity audit, the contract, Expo and Android identifiers, build
configuration affected by them, safe documentation, the lockfile policy, the
permission audit, validation, and the report.

Out, explicitly: internationalization, pt-BR, pseudo-localization, ads,
billing, leaderboards, accounts, backend, persistence, sharing, new music,
balancing, music sync, redesign, new mechanics, stage tuning. **No gameplay
value moves.**

## What the audit has to decide, not assume

Three questions the plan cannot answer in advance:

1. **Is the native Android directory committed or generated?** It decides
   whether `app.json` is authoritative or whether native files need migrating
   too. Migrating both would produce conflicting declarations.
2. **Does changing the slug break the EAS link?** The project id is external
   state. If it does, that is an owner action and not a code change.
3. **Is `RECORD_AUDIO` removable?** Only if the game provably never records
   *and* no dependency requires it. Removing a permission because it looks
   unnecessary is how audio breaks in release and not in debug.

Each is answered in the report with the evidence that answered it.

## Definition of done

Slug, package and bundle id migrated; no runtime or build configuration
carrying the old identity; a contract document; a regression test that fails if
the old identity returns through configuration; lockfile tracked; permissions
audited with evidence; typecheck, lint, tests and art gates green; the game
installing, launching and playing identically under the new package; and the
roadmap corrected so identity precedes i18n.

**M19 is not started.**
