## Three findings the audit produced that assumption would not have

### 1. Changing the slug breaks the EAS link

```
Slug for project identified by "extra.eas.projectId" (worst-band-ever)
does not match the "slug" field (worst-gig-ever)
```

The project id is authoritative and its server-side slug is still the old one.
**EAS builds fail until the project is renamed on expo.dev.** `eas-cli` 20.4.0
has no `project:rename`; this is a web action.

The project id was **not** changed and no new project was created. A new id
means new credentials and a different application on Expo's side — a far worse
outcome than a rename.

### 2. Removing `RECORD_AUDIO` from config was not enough

The obvious fix — drop it from `android.permissions`, set the plugin's
`microphonePermission: false` — produced a clean resolved Expo config *and an
APK that still requested the permission*.

The manifest merger report named the source:

```
uses-permission#android.permission.RECORD_AUDIO
ADDED from [expo.modules.audio:expo.modules.audio:0.4.9]
```

The library's own AAR manifest declares it. Only `android.blockedPermissions`,
which emits `tools:node="remove"`, actually removes it. **This was caught by
inspecting the built APK, not the config** — the config was already telling the
truth about itself and the wrong thing about the artifact.

Evidence that removal is safe: the game's entire audio surface is
`createAudioPlayer` and `setAudioModeAsync`. There is no `Recording`,
`recordAsync`, `useAudioRecorder` or permission request anywhere in `game/` or
`App.tsx`.

### 3. The lockfile ignore was a template default, not a decision

`.gitignore` ignored `yarn.lock` and `package-lock.json` together — the shape
of a template default rather than a project choice. `project-status.md` item 8
already attributed the ADR 0006 autolinking failure to it. The installed tree
matches the lockfile (`npm ls --depth=0` clean), so it was tracked as-is
without regenerating anything.
